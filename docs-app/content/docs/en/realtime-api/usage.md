# Realtime Usage

This document describes the token usage fields currently emitted by the
realtime backend.

## Scope

The current implementation accounts for `full_duplex` realtime sessions.
It reports actual token deltas from the model layer, converts them to the
public multimodal usage shape in the backend, and accumulates the result for
the lifetime of a session.

The existing inference fields and metrics are unchanged. Usage is additional
metadata on the existing realtime events.

## Usage Shape

Every usage snapshot has this shape:

```json
{
  "total_tokens": 123,
  "input_tokens": 100,
  "output_tokens": 23,
  "input_token_details": {
    "text_tokens": 20,
    "audio_tokens": 60,
    "vision_tokens": 20
  },
  "output_token_details": {
    "text_tokens": 5,
    "audio_tokens": 18
  }
}
```

The totals are derived from the detail fields:

```text
input_tokens  = text + audio + vision
output_tokens = text + audio
total_tokens   = input_tokens + output_tokens
```

## Counting Rules

The model reports token deltas for each operation. The backend does not
reconstruct the system prompt from the request or infer output counts from
string length.

### Session preparation

Preparation runs once when the duplex session is initialized:

- system prompt text contributes to `input_token_details.text_tokens`;
- reference audio contributes to `input_token_details.audio_tokens`.

These counts are included in the first `session.created.usage` snapshot.

### Per-input prefill

Each full-duplex input chunk contributes newly processed prefill tokens:

- unit and other text tokens contribute `text_tokens`;
- audio embedding rows contribute `audio_tokens`;
- all vision embedding tokens contribute `vision_tokens`, regardless of
  whether the source arrived as an image or video frame.

The prefill delta is counted when the model processes the input. It is not the
current KV-cache length, and tokens removed by a sliding window are not
subtracted from cumulative usage.

### Generation

Each generation operation contributes:

- generated LLM text tokens to `output_token_details.text_tokens`;
- generated TTS tokens to `output_token_details.audio_tokens`.

These values come from the model's generated token counts, not from the
number of characters or the byte length of returned audio.

## Event Placement

### `session.created`

The event contains a cumulative snapshot. It includes preparation usage and
is zero for fields that have not been processed yet.

```json
{
  "type": "session.created",
  "session_id": "sess_example",
  "usage": {
    "total_tokens": 80,
    "input_tokens": 80,
    "output_tokens": 0,
    "input_token_details": {
      "text_tokens": 24,
      "audio_tokens": 56,
      "vision_tokens": 0
    },
    "output_token_details": {
      "text_tokens": 0,
      "audio_tokens": 0
    }
  }
}
```

### `response.output.delta`

For each processed full-duplex input chunk, the first output event for that
chunk carries:

- `chunk_index`: zero-based input/output chunk index;
- `chunk_usage`: usage generated by this chunk only;
- `usage`: cumulative session usage after this chunk.

If one chunk produces both text and audio events, usage is attached to only
the first of those events. This prevents the same chunk from being counted
twice. The remaining event keeps its original text or audio payload without
duplicating usage fields.

Example:

```json
{
  "type": "response.output.delta",
  "kind": "text",
  "text": "Hello,",
  "chunk_index": 3,
  "chunk_usage": {
    "total_tokens": 34,
    "input_tokens": 28,
    "output_tokens": 6,
    "input_token_details": {
      "text_tokens": 1,
      "audio_tokens": 16,
      "vision_tokens": 11
    },
    "output_token_details": {
      "text_tokens": 2,
      "audio_tokens": 4
    }
  },
  "usage": {
    "total_tokens": 114,
    "input_tokens": 108,
    "output_tokens": 6,
    "input_token_details": {
      "text_tokens": 25,
      "audio_tokens": 72,
      "vision_tokens": 11
    },
    "output_token_details": {
      "text_tokens": 2,
      "audio_tokens": 4
    }
  }
}
```

### `session.closed`

The close event contains the final cumulative usage snapshot. It is also
included for fatal session termination when the server can send the close
event.

## Cumulative Semantics

`usage` is session-scoped and monotonically increases while the session is
active. `chunk_usage` is local to one input chunk. A new session starts from
zero and does not reuse usage from a previous session.

Usage is independent of wall-clock metrics, `kv_cache_length`, generated
audio duration, and the number of output events.

## Current Limitation

The usage fields described above are wired through the full-duplex realtime
path. The turn-based chat path currently keeps its existing response format
and does not yet report per-request token usage.
